# Dynasty

A BitLife-style multi-generational life simulator. This is a standalone rebuild — see [`docs/DYNASTY_HANDOFF.md`](docs/DYNASTY_HANDOFF.md) for the full design spec this was built against.

**Important context on this rebuild:** the original `dynasty.jsx` prototype (a single ~4,900-line React artifact that ran inside Claude.ai's sandbox) was not available when this rebuild started — only the design document. So this repo is a real, from-scratch implementation of that design: a genuine backend, database, and auth, but only a subset of the original's content and mechanics. See "What's implemented" below for the honest boundary.

## Stack

- **`shared/`** — TypeScript types and static game data (epochs, nations, career tracks) used by both server and client. This is the single source of truth for the `Character`/`Dynasty`/`TreeRecord` shapes (handoff doc Section 2).
- **`server/`** — Express + TypeScript API. Holds the deterministic turn engine, the Anthropic API key (never sent to the client), and talks to Supabase with the caller's own access token so Postgres Row Level Security does the authorization, not application code.
- **`client/`** — React + Vite + TypeScript. Thin UI; all game logic runs server-side.
- **Supabase** — Postgres + Auth. One table, `dynasty_saves`, storing a single JSONB blob per save slot (see "Persistence" below for why).

## Setup

```bash
npm install
cp server/.env.example server/.env       # fill in ANTHROPIC_API_KEY if you have one
cp client/.env.example client/.env.local
npm run dev:server   # http://localhost:8787
npm run dev:client   # http://localhost:5173
```

The Supabase URL/anon key in the `.env.example` files already point at a real project (`Tmitchell352's Project`) with the `dynasty_saves` table and RLS policies applied — see [`docs/DYNASTY_HANDOFF.md`](docs/DYNASTY_HANDOFF.md) for schema details. That project also hosts an unrelated existing app (`firms`/`clients`/`matters`/etc. tables) — Dynasty only touches `dynasty_saves`.

Without `ANTHROPIC_API_KEY` set, the game still fully works — every turn falls back to the deterministic narrative (the original's "No AI Narration" mode), per Section 9 of the handoff doc.

## What's implemented

- Full `Character`/`Dynasty`/`TreeRecord` type system (handoff Section 2).
- All 20 epochs with correct id/year/label/currency, and nation counts matching Section 4's table (9 nations for each of the first 8 ancient epochs, 6 for the remaining 12 — 116 unique nations total, close to the spec's 111 target). This is an independently-researched roster of real, period-appropriate historical polities, not a port of the original's actual list (that content lived only in the unavailable source file) — validated by a script confirming every nation has a matching NPC and continent entry and every epoch hits its target count.
- All 10 career tracks' title ladders and salaries, in all 4 era-appropriate dictionaries (Section 5) — and now all 10 tracks' *distinct* mechanics from Section 5's table are wired into the engine (`server/src/game/engine/tracks.ts`): Political's elite/commoner standing split, Military's campaign injury/death risk, Religious's uncapped followers with schism risk, Criminal's heat meter with bribe/flee/imprison resolution, Academic's named treatises, Commercial's major-deal coin-flip, Medical's skill-weighted difficult cases, Maritime's voyage risk, Artisan's masterworks, and Sports's persistent rival with win/loss record and endorsement deals.
- **Specializations and Change Career** (Section 5's "Cross-track systems"): every `TrackDef` has carried 3 specializations (a one-time stat perk) since the first commit, but nothing ever let a player actually choose one. `chooseSpecialization`/`changeCareer` (`server/src/game/engine/tracks.ts`, exposed as `POST /turn/:slotIndex/choose-specialization` and `POST /turn/:slotIndex/change-career`) fix that: PlayScreen shows a "Career" section once a character is 18+ with a track, offering the specialization choice (if not already made) and a "Change Career" track switch (resets to tier 0, a small popularity cost, but any specialization already earned in a track is remembered if the player switches back to it later).
- **Family traditions** (Section 5's "Cross-track systems": "chosen once at founding — permanent bonus to all future descendants who settle into a matching track"): `Dynasty.tradition` existed since the first commit but was never selectable at founding and never mechanically applied - it was pure flavor text fed into the AI prompt context. CreateScreen now has a real tradition selector, and `applyFamilyTradition` (`server/src/game/engine/tracks.ts`) grants a real one-time stat bonus (gated by `Character._traditionAppliedTracks`, so it can't be re-earned by switching away and back via Change Career) the first time a descendant enters the matching track - at coming-of-age or via a career change.
- The deterministic per-turn engine (`server/src/game/engine/turn.ts`), covering most of Section 9's numbered turn structure: aging, salary/property income, health regen, debt interest, old-age decay, reputation and domestic-bond decay (including the fix for the original's one-way rival-tension bug), NPC/children aging, coming-of-age track assignment, mortality rolls, tier promotion, and world-event/nation-power drift.
- **Era-accurate mortality** (`server/src/game/engine/mortality.ts`): death timing used to run on a single flat age/health curve no matter what year the character was living in, so a Bronze Age farmer and a 21st-century professional had identical odds of reaching 80. Two small piecewise-linear tables keyed on in-game year now drive it - a target adult lifespan (45 in the Bronze Age climbing to 80 by 2000) and a childhood-mortality multiplier (6x in the Bronze Age down to 0.12x today) - reflecting that historically child mortality fell decades before adult lifespan meaningfully extended. The same `eraAdjustedAge` scaling is applied to spouse, mentor/rival/friend/protege, and background-sibling mortality in `family.ts`, so every death in the game - not just the player character's - lands on a period-appropriate timeline instead of a modern one.
- **Broader life events** (Section 9 step 10, `server/src/game/engine/lifeEvents.ts`): previously a turn with no milestone, no track-specific event, and nothing from geopolitics or family was carried entirely by the single AI/fallback narrative line. A small pool of ambient flavor events - family reunion, family council, sibling interaction, protege growth, a marriage-prospects notice, a conversion-opportunity nudge, a court-faction overture - now has a real (if low, ~35%/year gated) chance to fire, each a small log-only beat with a modest stat/relation effect. Marriage, parenting, conversion, and faction support stay explicit player actions elsewhere (this rebuild's established split of "ambient effects tick automatically, real choices are routes") - these are the missing ambient layer, and the marriage/conversion ones double as nudges toward those actions instead of the player having to think to check.
- **All 4 AI call sites from Section 9's "only 4 things call the AI" rule** (`server/src/game/ai/eventGenerator.ts`), each using the Anthropic TypeScript SDK server-side with a deterministic fallback when no key is configured or the model output fails validation: `generateEvent` (the per-turn narrative), `generateSuitors` (marriage prospects — falls back to the deterministic 3-suitor generator in `family.ts`), `resolveCustomAction` (the free-text "try something" action exposed as `/turn/:slotIndex/custom-action` and a text input on PlayScreen — every stat delta the model returns is clamped server-side to fixed bounds regardless of what the JSON says, so a malformed or adversarial response can't blow past normal turn-to-turn stat swings), and `writeEulogy`/`writeChronicle` (on-demand narrative summaries, exposed as `GET /turn/:slotIndex/eulogy` and `GET /dynasties/:slotIndex/chronicle`, cached on `dynasty.biographies`/`dynasty.chronicleText`). GameOverScreen now has "Read Eulogy" and "View Dynasty Chronicle" buttons that call these on demand.
- **Geopolitical systems** (Section 6, `server/src/game/engine/geopolitics.ts`): world relations (initialized per nation at founding, merged between character and dynasty), military-track conquest with permanent recording and integration-crisis decay (including nations breaking free if neglected), throne rebellion against unpopular rulers, the coup-flavored "seize power" path for any non-political track at max tier, alliances with the automatic rival-souring side effect, espionage as a legacy-point-gated Dynasty Action, religious/cultural conversion with recurring suspicion, court faction support (and the neglect penalty below 15 standing), and succession crises when a ruler dies leaving a child heir. The automatic pieces (integration decay, throne rebellion, faction neglect, conversion suspicion) tick every turn; the rest are explicit player actions exposed under `/geopolitics/:slotIndex/*` since they're real choices, not scripted turn events.
- **Epoch drift and branching historical milestones** (Section 1 / Section 6's last bullet, `server/src/game/engine/milestones.ts`): `nearestEpoch()` existed since the first commit but was never called - characters now actually drift into new epochs as the in-game year advances, tracked in `_erasWitnessed`. 26 fixed historical milestones (the Great Pyramid to the 2008 financial crisis) fire once per dynasty; 21 apply a flat nation-power delta automatically, and 5 (Caesar's assassination, the Black Death, the French Revolution, 1848, 2008) are real branching choices that pause the turn - `/turn/:slotIndex/advance` refuses to run again until the player answers via `/turn/:slotIndex/resolve-milestone` - with the choice's effects recorded on the dynasty.
- **Achievements and victory conditions** (Section 9's step 1, `server/src/game/engine/achievements.ts`): 17 achievements checked every turn, each first-ever unlock granting legacy points (which had no earn path before this - only espionage's spend path existed); the three victory goals (10th generation / 300 or 750 legacy points), selectable at dynasty founding. A real crisis catalogue (plague/famine/war/unrest) was added alongside this, since `Dynasty.activeCrisis` was previously only ever decremented or nulled, never actually created.
- **Family systems** (Section 8, `server/src/game/engine/family.ts`): marriage via 3 AI-generated suitor prospects when a key is configured (`generateSuitors`), falling back to a deterministic generator in No AI Narration mode, including an arranged-alliance option tied to world relations - which now also carries its own explicit dowry payment (Section 7's "the arranged-alliance-marriage option includes an explicit dowry payment"), separate from the suitor's own personal wealthDelta/dowry; children being born to married couples; active parenting choices (strict/permissive/educate/labor) that accumulate on a child and convert into real starting-stat bonuses once they become the playable heir, distinct from passively-inherited traits; mentor/rival/friend/protege acquisition and mortality risk (these previously only ever aged or died off *if* already set - nothing anywhere ever assigned one, so in normal play a character could never actually have a mentor); spouse mortality risk; and a cheap background simulation for unplayed siblings (real death risk, no full parallel family tree). Marriage and parenting are explicit player actions under `/family/:slotIndex/*`; births, NPC acquisition, and mortality tick automatically every turn.
- **The Almanac now records anyone it names** (`Dynasty.almanac`, another field unused since the first commit): spouses, mentors, rivals (including schism and sports rivals), friends, and proteges are all remembered the moment they're named.
- **Will styles now do something** (Section 7/8): inheritance friction on the deceased's wealth (22% with no planning, down to 8% with both a written will and a family seat - matching the spec's exact figures) is computed by the shared `computeInheritanceFriction` helper (`shared/src/economy.ts`) so the server (which applies it in choose-heir) and the client can never disagree on the number - GameOverScreen now previews the exact friction percentage and each child's resulting inherited wealth *before* the player commits to an heir, instead of the cut only showing up after the fact. An `eldestFavored`/`youngestFavored` will that passes over the actual eldest/youngest child also gives the new heir a built-in starting rival in that sibling. `willStyle` and `familySeat` themselves were only ever factory defaults until now - nothing anywhere let the player actually change either one, so the friction math they feed could never move: Estate's new "Legacy Planning" section lets the player draw up a will (`POST /economy/:slotIndex/set-will-style`) and build a one-time 400-wealth family seat (`POST /economy/:slotIndex/build-family-seat`), with the same friction preview shown live.
- **Economy depth** (Section 7, `shared/src/economy.ts` + `server/src/game/engine/economy.ts`): the 6 property tiers from cottage to grand estate (each with a real purchase cost, one-time stat bonus, and recurring yearly income - property income used to be a flat +5 regardless of tier, since the tiers themselves didn't exist yet), a single-slot loan you can take and repay (interest already compounded yearly, but there was previously no way to actually take one on), a general-economy risky venture (5-tier outcome table, total loss to 4.5x return, independent of the Maritime/Commercial track events), and gifting to a spouse or a still-minor child (`giftedWealth` on `Child` existed in the type since the first commit but nothing ever set it). Exposed under `/economy/:slotIndex/*`.
- **Automatic economic events** (`server/src/game/engine/economicEvents.ts`): previously the economy only ever moved when the player remembered to visit Estate - salary and property income aside, a character's wealth was otherwise static. A small pool of turn-state-triggered events now has a real (~25%/year) chance to fire: a windfall inheritance, a theft (scaled to current wealth), a tax levy on anyone of real track standing, a market downturn for property owners, and a scaled-down automatic version of Estate's risky venture. A separate roll from the life-events one above, so an economic beat doesn't crowd out a social one in the same turn.
- **The rest of Section 9 step 12** (`server/src/game/engine/turn.ts` + `legendaryEvents.ts`): an advisor is now actually assigned at coming-of-age alongside the track (`Character.advisorName` existed since the first commit with nothing setting it - "track assignment + advisor" per step 11), a narrative-only health warning fires when health drops critically low, and a rare (~2%/year) **legendary event roll** grants a genuinely memorable, higher-magnitude moment - a brush with history, a feat of daring, a stroke of brilliance, an extraordinary windfall, or a heroic act - each with a real stat boost and 5 legacy points, distinct from the routine `lifeEvents.ts`/`economicEvents.ts` pools.
- Auth, save/load, turn-advance, choose-heir, geopolitical-action, family-action, and economy-action routes, backed by Supabase Auth + Postgres with RLS.
- **The persistence bug class from Section 10 is designed out structurally**: `server/src/game/engine/persistence.ts` is the single `serializeDynasty`/`deserializeDynasty` choke point every route uses, and `dynasty_saves.dynasty` is one JSONB column — there is no second or third place a new field can be forgotten.
- A React client covering the golden path (login → slots → create → play → death → choose heir, including choosing a victory goal at founding) plus Section 3's single Menu hub leading to all ten of its secondary screens: **Family**, **Dynasty Actions**, **Estate** (buy property, take/repay a loan, risky ventures, gift to spouse or children, and Legacy Planning - see above), **Codex** (achievement progress and legacy points), **History** (the dynasty's event ticker), **Almanac** (named NPCs encountered), **Records** (dynasty-wide superlatives - wealthiest, most influential/skilled/popular, longest-lived, most decorated, and every throne holder), **Family Tree** (every recorded person grouped by generation), **Timeline** (History's event ticker merged with every recorded person's birth and death, sorted into one chronological narrative - distinct from History, which is world/milestone events only), and **Settings** (a real, if small, toggle: `noAiMode` existed on `Dynasty` since the first commit with no way to ever set it away from its factory default of false - now it's a real switch - plus a read-only display of the dynasty's founding configuration, which previously wasn't shown anywhere in the client). PlayScreen also renders a pending branching milestone's choices in place of "Advance a Year" when one is waiting, and now correctly redirects to heir selection if the loaded save's character has already died (previously it would render the play screen for a dead character if the app was reopened between death and choosing an heir).
- **Ad support** (`client/src/ads.ts` + `client/src/components/AdSlot.tsx`), off by default. Per the handoff doc's own Section 12, ads only make sense "once this is a genuinely independent app with its own backend" - which this now is - but there's no way to fabricate a working ad integration without a real ad network account, so what's here is the standard Google AdSense embed pattern (script injection + `<ins class="adsbygoogle">`), gated behind `VITE_ADS_ENABLED`/`VITE_ADSENSE_CLIENT_ID`/`VITE_ADSENSE_SLOT_ID`. With those unset it renders nothing in production and an explicit "not configured" marker in dev. Placed on the slots list and the between-lives screen. Turning it on for real requires your own AdSense account; if this app is ever embedded back into a Claude.ai/Claude Code surface, ads must stay off there regardless of these env vars.

## What's NOT implemented yet

All ten of Section 3's secondary screens exist, and the economy now moves on its own as well as by player action. What's left:

1. Real ad serving requires supplying your own AdSense credentials - see "Ad support" above. That requires an account only you can create, so it's the one item here not resolvable by more engine/UI work.

## Testing note: Supabase is unreachable from a Claude Code cloud/remote session

If you're running this from a sandboxed Claude Code environment (as this repo was built in), outbound HTTPS to `*.supabase.co` is blocked by the session's egress policy (confirmed via the agent-proxy status endpoint: `403` / "policy denial" on the `CONNECT` to `supabase.co`). That means the real Supabase-backed HTTP routes can't be exercised end-to-end from inside such a session against the real backend. Two workarounds were used across this project's development, both temporary and never committed: (1) mocking the browser's own network calls (Supabase auth + the API responses) via Playwright's `page.route()`, verifying client render/state/event-handling in isolation; (2) for a fuller check, temporarily swapping `server/src/supabase.ts`'s real `createClient` for a small in-memory stand-in implementing just the query-builder chain the routes use (`.from().select().eq().eq()[.order()][.maybeSingle()/.single()]`, `.update()`, `.delete()`, `.upsert()`), then running the *real* Express server and *real* engine against it, driven by a real browser with only the client's own Supabase sign-in call mocked - this exercises the actual route handlers and game logic end-to-end, not just canned JSON. If you're running locally (not sandboxed), neither workaround is necessary and the app should reach Supabase normally.

## Known issue surfaced during setup

The Supabase project this repo uses (`Tmitchell352's Project`) has **Row Level Security disabled on its other 8 tables** (`firms`, `users`, `clients`, `matters`, `deadlines`, `documents`, `invoices`, `subscriptions`) — unrelated to Dynasty, but worth fixing if that app is in active use. `dynasty_saves` itself has RLS enabled with owner-only policies.
